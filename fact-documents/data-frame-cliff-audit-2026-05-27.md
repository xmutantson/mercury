# Data-frame cliff audit (2026-05-27)

**Status:** investigation complete, awaiting fix authorization
**Origin:** Hardware Wave-3 A/B test (`b_mfsk_connect_w3_test/v1/b_mfsk_logs/`) on monitor
`41ac734` showed a 4–6 dB gap between CONNECT (which decodes at WGN:−8) and DATA
(which dies at WGN:−4 to −8). Both layers use the SAME M=16-Welch-Costas / M=32-MFSK
modulation; CONNECT survives substantially below where DATA dies. The mystery the
parent agent asked me to resolve.

This document is the §1–§4 trace per the original prompt. Punch list in §5.

## §1. The anomaly, exactly

| WGN | data bps | HAIL OK? | CONNECT-START OK? | DATA preamble OK? |
|---|---|---|---|---|
| +14 | 3.8 | yes | yes | **62%** (23 OK / 4 NP / 11 FAIL of 38 polls) |
| +6  | 3.6 | yes | yes | (similar) |
| 0   | 3.6 | yes | yes | **58%** (22 OK / 4 NP / 12 FAIL of 38 polls) |
| −4  | 1.1 | yes | yes | **10%** (18 OK / 150 NP / 6 FAIL of 174 polls) |
| **−8** | **0** | **yes** (metric 8.8, base 16/8 suffix 4/4) | **yes** (matched=15/16, CRC12 occasionally fails) | **0%** (0 OK / 320 NP / 0 FAIL) |
| −12 | 0   | no  | n/a | n/a |

(Counts via `grep -c "RX-DECODE.*<state>" b_mfsk_wgn{14,0,-4,-8}_rsp.log`.)

**"NP" = NO-PREAMBLE.** That's the `[RX-DECODE#N] NO-PREAMBLE: mfsk_raw=...` log path
in `mercury/source/datalink_layer/arq_common.cc:5798-5804`, fired when
`receive_msg()` returns `delay == -1` (no MFSK sync). At WGN:−8, 100% of 320
DATA-RX poll cycles fail with NO-PREAMBLE. The RSP log shows zero `RX-DECODE OK`.

CONNECT, by contrast, **reliably** decodes at WGN:−8 (in
`b_mfsk_wgn-8_rsp.log`: `[RX-MFSK-CTRL-CONNECT-START] sender='TESTA'` cycles
~9× over the 180 s dwell). CMD also reports `[RX-MFSK-CTRL-CONNECT-ACK]
echoed_cap=0x01 own_cap=0x01` — full bidirectional CONNECT handshake at
WGN:−8.

**Conclusion: the cliff is in MFSK DATA preamble sync, not in MFSK decoder, not
in LDPC.** Frames never reach the LDPC decoder because the preamble detector
returns `-1`. `iter_mean==1` in successful cells confirms LDPC isn't the
bottleneck — when frames *do* arrive, LDPC converges instantly.

## §2. The two RX paths, side-by-side

### §2.1. MFSK DATA RX path (the one that fails)

Entry point: `cl_telecom_system::receive_msg`
(`mercury/source/physical_layer/telecom_system.cc:~830`).

Step-by-step:

1. **Passband → baseband decimation** (`telecom_system.cc:951-979`).
   `passband_to_baseband()` with `FIR_rx_time_sync` on the FULL-RATE buffer
   for MFSK; OFDM uses the decimated buffer. MFSK keeps full-rate because
   `time_sync_mfsk_corr` does a 4× oversampled Phase-1 search (Bug #44).
2. **Preamble sync — `time_sync_mfsk_corr`** at `ofdm.cc:3021-3221`.
   - Template: 4 symbols × 292 baseband samples = **1168 decimated samples**
     (~97 ms in baseband time), generated by FIR-round-tripping the known
     preamble waveform through the TX/RX chain (`telecom_system.cc:4948-5015`).
   - For each candidate position (4× oversampled symbol grid via
     `P1_OVERSAMPLE=4`, `p1_step = sym_period_interp/4`):
       - Computes per-symbol normalized cross-correlation
         `|<rx, template>|² / (||template||² * ||rx||²)`
         (cosine-similarity squared) over Nofdm = 292 samples.
       - **PER-SYMBOL FLOOR**: `per_sym_floor = 0.05` at `ofdm.cc:3061`. If
         **any** of the 4 symbols falls below 0.05 the candidate is rejected
         (`rejected = true`, `break`).
       - Otherwise averages across symbols → metric.
   - Returns `-1` if no candidate survived the per-symbol floor.
3. **Time-domain delay** propagated to `received_message_stats.delay`. If
   negative, `receive_msg()` returns early with `message_decoded = NO`
   (`telecom_system.cc:1068-1075`).
4. **Frame extraction** (only if delay >= 0). Reads `preamble_nSymb + Nsymb =
   4 + 320 = 324` symbols starting at the delay.
5. **MFSK demap** at `mfsk.cc:~750` (F2 log-sum-exp, post-Phase-0). Produces
   LLRs.
6. **LDPC SPA** (`ldpc_decoder_SPA.cc`), 200-iter cap for ROBUST_0 (Q3),
   outer CRC16.

**Key parameter (ROBUST_0 WB)**:
- M (alphabet) = 32, nStreams = 1 (`telecom_system.cc:4890-4892`)
- `preamble_nSymb = 4`, tones `{4, 20, 12, 28}` (`mfsk.cc:122-129`)
- Nofdm = 292 (Nfft=256 + Ngi=36 = 256+36)
- Total preamble waveform = 4 × 292 × interp_rate(4) = **4672 passband samples = 97.3 ms**

### §2.2. MFSK CONNECT RX path (the one that works)

Entry point: `cl_telecom_system::decode_ctrl_suffix_from_passband`
(`telecom_system.cc:3362-3436`).

Step-by-step:

1. **Passband → baseband decimation** (`telecom_system.cc:3376-3382`).
   Polyphase decimated. Carrier uses `last_coarse_freq_offset` correction.
2. **Base pattern detection — `detect_ack_pattern`** at `ofdm.cc:3231+`.
   - Sliding-window FFT-bin-argmax matched filter over the
     **`connect_pattern_nsymb = 16`** symbols (`mfsk.cc:347-356`,
     M=32 case: 2× scaled M=16 Welch-Costas g=3, tones
     `{6, 18, 20, 26, 10, 30, 22, 16}`).
   - For each symbol p in 0..15, decode-and-FFT a 292-sample window. Find
     peak bin within stream's M=32 bins; if peak == expected, `matched++`.
     No per-symbol floor.
   - `metric` accumulates `e_target/e_total` per symbol.
   - Reserves `reserve_after = ack_sack_suffix_len() = 13` symbols.
3. **Gate**: `matched >= connect_match_threshold (=7)` AND `metric >= 3.0`
   AND `best_offset >= 0` (`telecom_system.cc:3399`). Note: threshold is
   **7/16** for both ACK and CONNECT-base.
4. **Phase-2 fine timing refinement** at `ofdm.cc:3389+` — always-fine when
   `best_matched >= 6`, searches ±Nofdm/2 at base-rate resolution.
5. **Suffix decode** (13 symbols of 5-bit FFT-bin-argmax tones) at
   `telecom_system.cc:3407-3414`. Returns the tones (5-bit per symbol → 65
   bits, of which 13 type + 38 payload + 12 CRC12 = 63 used; see
   `mfsk_ctrl_codec.cc` for layout).
6. **CRC12 check** in `ack_mfsk.decode_ctrl_suffix_from_last_capture()`.
   Returns true only if CRC matches.

**Key parameter (CONNECT base, ROBUST_0 WB)**:
- M (alphabet) = 16 for ack_mfsk family (`telecom_system.cc:5252`), regardless
  of data-config M. WB always uses ack_M=16.

  Wait — for ROBUST_0 the data config is M=32 but ack_mfsk is M=16. The
  CONNECT base pattern at M=32 (`mfsk.cc:347-356`) uses scaled M=16
  values. Looking at the actual init at `telecom_system.cc:5252`: `ack_M =
  narrowband_enabled ? 8 : 16` — so **ack_mfsk for ALL WB configs uses M=16**.
  The M=32 connect_tones block in `mfsk.cc` would only fire if ack_mfsk itself
  ran at M=32, which it doesn't for any config. So at runtime, CONNECT
  always uses M=16 base regardless of data M.
- `connect_pattern_nsymb = 16` (`mfsk.cc:353` for M=32 branch; equivalent
  M=16 line at 360)
- `connect_match_threshold = 7/16` (`mfsk.cc:354/361`)
- Total base waveform = 16 × 292 × interp_rate(4) = **18688 passband samples
  = 389 ms** (confirmed in log: `[PHY] ACK pattern: 16 symbols (M=16, WB
  Welch-Costas), 18688 passband samples (389 ms)`).
- Suffix: 13 symbols × 292 × 4 = 15184 samples = 316 ms.
- **Total CONNECT detection waveform: 29 symbols = 705 ms.**

### §2.3. Side-by-side diff

| Stage | CONNECT | DATA preamble | Failure-mode delta at low SNR |
|---|---|---|---|
| **Integration length (base)** | 16 sym × 292 = 4672 dec smp / **389 ms** | 4 sym × 292 = 1168 dec smp / **97 ms** | **4× more integration in CONNECT → +6 dB matched-filter SNR gain** |
| **Modulation order during detection** | M=16 (1 in 16 = 6.25% random match) | M=32 (1 in 32 = 3.1% random match) | Data has lower random-match floor but ALSO lower per-symbol energy in the right bin (signal split over more bins / less symbol margin) |
| **Metric type** | Discrete: count symbols where expected bin == peak bin (FFT argmax) | Continuous: cosine-similarity per symbol; **per_sym_floor=0.05** rejection on ANY single bad symbol | DATA fails on a SINGLE bad symbol; CONNECT degrades gracefully |
| **Threshold form** | matched ≥ 7/16 AND metric ≥ 3.0 (cumulative) | best_metric ≥ avg(per_sym) over all 4 — and all 4 must pass 0.05 floor | DATA's floor is a hard cliff; CONNECT's cumulative threshold can absorb 9 bad symbols |
| **Phase-2 refinement** | Yes, always-fine when matched ≥ 6 | Yes, top-K Phase-1 then base-rate refine | Comparable |
| **Channel estimate** | None (FFT-bin-argmax, noncoherent) | None for preamble (MFSK is noncoherent); only for data demap | Identical for sync stage |
| **CFO sensitivity** | Uses `last_coarse_freq_offset` correction (`telecom_system.cc:3378`) | Mostly noncoherent — but FIR_rx_time_sync band-passes around carrier, so CFO drift outside the FIR window kills both equally | Comparable; CONNECT slightly worse because longer integration accumulates more rotation |
| **Frame duration after sync** | 29 symbols total (one shot) | 324 symbols (preamble + 320 data); decoded as ONE LDPC codeword | DATA needs sync to hold across many more symbols, BUT this only matters AFTER sync; here the failure is BEFORE sync |

**The dominant differentiator is integration length × per-symbol floor.** CONNECT
integrates over 4× longer time AND uses a softer threshold AND can tolerate up
to 9 individual bad symbols. The MFSK DATA preamble has neither margin.

## §3. Ranked failure-mode hypotheses

### **H1 — Data preamble is too short (rank: PRIMARY, near-certain)**

**Evidence:**
- `preamble_nSymb = 4` for M=32 WB (`mfsk.cc:124`).
- `preamble_nSymb = 4` for M=16 WB (`mfsk.cc:132`) — same 4 symbols across
  the entire WB family, INCLUDING ROBUST_0/1/2 and all OFDM data configs.
- NB ROBUST_0 (M=8) uses `preamble_nSymb = 8` (`mfsk.cc:141`) — already 2×
  longer. NB doesn't exhibit the same severity at WGN:−8 (no NB data was
  in this test cell, but design margin is structurally better).
- CONNECT's 16-symbol base = 4× integration ≈ +6 dB matched-filter SNR.
  The cliff position (DATA fails at WGN:−4 to −8 while CONNECT works at
  WGN:−8) maps cleanly to a 4–6 dB sensitivity gap.

**Test (no code change required):** simulate. Inject a known data frame at
WGN:−8 into the existing simulator (`mercury.exe -m PLOT_PASSBAND -s 100`),
extend `preamble_nSymb` from 4 to 16 and observe whether `time_sync_mfsk_corr`
returns valid delays where today it returns −1. Even a 4→8 step (matching the
NB count) should buy ~3 dB.

**Estimated win:**
- 4→8 symbols (2× integration): +3 dB matched-filter SNR.
- 4→16 symbols (4× integration, matches CONNECT base): +6 dB matched-filter
  SNR.
- Caveat: stretches the per-frame overhead from 4 × 22.67 ms = 90 ms to
  362 ms preamble for ROBUST_0. At 84 bps PHY (5.2 s data per frame) the
  overhead bump is 5% relative — acceptable.

**Why this is the highest-confidence hypothesis:** it's the only difference
between CONNECT and DATA that maps directly to the observed dB-floor gap, and
it requires no new measurements to confirm — the math is on the page.

### **H2 — Per-symbol floor is too strict (rank: SECONDARY, contributing)**

**Evidence:**
- `per_sym_floor = 0.05` at `ofdm.cc:3061`. ONE symbol below this in the 4-symbol
  preamble → entire candidate rejected → no fallback to less-strict matching.
- Cosine-similarity per symbol over Nofdm=292 samples; for white noise the
  expected value is ≈ 1/(2·292) ≈ 0.0017. The floor 0.05 is 30× noise floor —
  intended to reject pure noise, but ALSO rejects valid preambles that suffer
  a momentary fade or burst on one symbol.
- The harsh impact compounds with H1: with only 4 symbols, ANY single bad
  symbol kills the whole detection. With 16 symbols, you can tolerate 12+
  bad ones (CONNECT does, via matched-counting).

**Test:** drop `per_sym_floor` from 0.05 to 0.01 (10× over noise floor still
prevents false positives; same as raising the noise reject by ~7 dB). If
preamble detection succeeds at WGN:−4 cells where it currently fails 90%
of the time, this is contributing.

**Estimated win:** +1 to +2 dB, on top of H1. Independent.

### **H3 — Per-symbol floor uses cosine similarity instead of summed energy ratio (rank: TERTIARY, structural)**

**Evidence:**
- `time_sync_mfsk_corr` uses normalized cross-correlation per symbol then
  rejects on minimum across symbols (`ofdm.cc:3086-3097`).
- `time_sync_mfsk` (the FFT-energy fallback at `ofdm.cc:2866-3008`) sums
  energy ratios across symbols, no per-symbol floor, threshold is `nSymb *
  0.5 = 2.0` for the 4-symbol WB preamble.
- The FFT-energy path is what mid-2025 logs used; at some point the corr-template
  path became the default. Empirical question: was the energy-ratio variant
  more robust at low SNR?
- This is essentially the soft-decision-vs-hard-decision argument from §2.3.

**Test:** disable the corr-template path (set `ofdm.mfsk_corr_template = NULL`
at runtime) and re-run the WGN:−8 cell. If FFT-energy mode decodes where
corr-template fails, switch the default or run both and OR the result.

**Caveat:** Bug #44 fix preferred `time_sync_mfsk_corr` for "2000:1 noise
discrimination" — but that was measured at HIGHER SNR. At WGN:−8 the
discrimination claim doesn't hold (template is too short to differentiate).
The fix might be to use ENERGY-RATIO at low SNR (longer integration window,
fewer false negatives) and CORR-TEMPLATE at high SNR (better discrimination
when many strong false-peak candidates exist).

**Estimated win:** uncertain; possibly +0.5 to +1.5 dB if FFT-energy is more
robust at the cliff.

### **H4 — Channel estimation at WGN:−8 produces garbage [RULED OUT for this cliff]**

LDPC `iter_mean == 1` when frames DO arrive. Channel estimate is the
post-sync stage; sync never succeeds, so this is downstream of the failure
point. The Phase 0 A.1.4 cross-pilot fix is still relevant for the
post-sync-recovery dB budget — but it cannot move the WGN:−8 cliff because
that cliff is BEFORE channel estimation.

### **H5 — Batch-level coherence drift [RULED OUT]**

Even on a single frame the preamble fails. There's no batch-level drift
problem to investigate at this cliff. Drift becomes relevant AFTER sync
works — Phase 1 of the parity plan.

### **H6 — Different operating-point parameter [SECONDARY EXAMINATION]**

`MOD_MFSK_DATA` doesn't exist as a separate enum; ROBUST_0 uses `MOD_MFSK`
(`mfsk.h:34, #define MOD_MFSK 200`) for both control and data frames.
However, **M differs**: data is M=32 / nStreams=1, while CONNECT and ACK
patterns are M=16 / nStreams=1. This subtle asymmetry IS one factor in
the cliff position, but it's a SECONDARY effect compared to integration
length:

- M=32 splits signal energy across more bins per FFT-window → expected
  per-bin SNR is ~3 dB lower than at M=16.
- BUT the matched-filter detector is per-symbol — it doesn't suffer the
  full M× spread because it correlates against ONE expected tone.
- Plausible contribution: +1 to +2 dB if data preamble were dropped to
  M=16 (alphabet, not data — preamble alphabet is independent of data
  alphabet in principle).

This is the kind of fix that needs an architectural discussion: changing
preamble M=32→M=16 means re-tuning the M=32 channel-estimation pilots if
those exist (they don't for MFSK — channel estimation is pure tone-energy,
no pilot symbols). Worth flagging in §5.

### **H7 — Phase B Wave 3 dispatch broke DATA-RX as a side effect**

Wave 3 was eec768e (Site B) and 41ac734 (Site F). User explicitly flagged
this as a hypothesis to check. The fix in those commits added gates on
the CONNECT-suffix-frame consumer paths (CONTROL message synthesis after
HAIL race delay). Mechanism by which it could affect DATA: if a code path
that used to deliver synchronization state (last_coarse_freq_offset,
mfsk_search_raw reset, etc.) was gated out, the data RX path could be
missing essential state.

**Test:** bisect from `9c3fc40` (pre-Phase-B) → `eec768e` (Site B) → `41ac734`
(Site F). Pinned ROBUST_0 axis_walk_sweep at WGN ∈ {14, 0, −4}. If DATA bps
collapses between `9c3fc40` and `41ac734` even at WGN:0 or +14, H7 is
confirmed. If it doesn't, H7 is refuted and H1 carries.

**Pre-test reading of evidence:** ALL cells WGN ≥ −4 had non-zero data
delivery (3.8 bps at WGN:+14, 3.6 bps at WGN:0 and −4). The 3.8 figure is
unchanged from the Phase 0 baseline (`mfsk_vara_parity_audit_2026_05_25.md`
recorded 3.8 bps at WGN:+14 pre-Phase-B). So Phase B did NOT regress easy
cells. **H7 is unlikely** but the bisect is cheap (one Pi-pair, 4 cells × 90 s
= ~6 min/commit × 3 commits = 20 min).

## §4. Smoking-gun log evidence

The single smoking gun: `b_mfsk_wgn-8_rsp.log` shows **320/320 RX-DECODE
attempts returning NO-PREAMBLE** (`mfsk_raw=0`, the search cursor finds
nothing across the buffer). Same log shows ~9 successful CONNECT-START
decodes and HAIL detections in the same dwell window. Same RX path, same
audio buffer — only the preamble-sync stage differs.

In the WGN:−4 cell, NO-PREAMBLE drops to 86% (150/174) and OK rises to 10%
(18/174). This is a steep cliff between WGN:−4 and WGN:−8 — exactly where
a +6 dB integration-length gap would put the boundary.

**Cross-check via Phase 0 cliff sweep:**
[`mfsk_vara_parity_audit_2026_05_25.md` §"Phase 0 RESULTS"] reported
data cliff at WGN:−2 to −6 with the SAME 4-symbol preamble (Phase 0 didn't
touch sync). The data layer is in fact CONNECT-detector-bound — that's why
single-cell variance shows up. After Phase B added MFSK CONNECT, CONNECT
extended its floor to WGN:−8, but the data floor stayed where it was
because nothing touched sync.

## §5. Recommended fixes, hardware experiments, and queued decisions

### Smoking-gun finding — no further test needed

**H1 is the dominant cause.** The data preamble is structurally 4× shorter
than the CONNECT pattern that demonstrably works at WGN:−8. The fix is
to lengthen the data preamble. There is no microphone-level instrumentation
needed; the integration-length math closes the case.

### Top fix (recommended)

**Fix #1 — Extend MFSK data preamble from 4 → 16 symbols** (`mfsk.cc:122-137`).

Use 4 reps of the existing Welch-Costas g-something base (or 4 reps of the
current {4,20,12,28} tones with hopping by `tone_hop_step` to break
periodicity, exactly like CONNECT does at `ofdm.cc:3282`). This:

1. Yields 4× matched-filter integration gain → **+6 dB sensitivity**.
2. Reuses the existing `time_sync_mfsk_corr` infrastructure — the only
   change is `preamble_nSymb` and the corresponding `preamble_tones[]`
   array.
3. Adds ~270 ms per frame at ROBUST_0 (4× 22.67 ms × 3 extra symbols);
   relative overhead bump at 5.2 s/frame is < 6%.
4. Both sides must agree — TX generation reads the same array, so this
   is a one-file change but BOTH endpoints must rebuild together. (Standard
   PHY-change discipline.)

**Estimated dB win: 6 dB at the cliff.** Cliff moves from WGN:−4 to ~WGN:−10
on this single change — likely matches CONNECT's current floor and may
reveal H2/H3 as the next bottleneck.

### Phase 2 fix (queued, only if Phase 1 doesn't close the gap)

**Fix #2 — Soften `per_sym_floor` from 0.05 → 0.01 or use min-of-top-3
robust statistic** (`ofdm.cc:3061`). +1 to +2 dB more, on top of Fix #1.

**Fix #3 — Adaptive sync algorithm**: use FFT-energy (`time_sync_mfsk`,
`ofdm.cc:2866`) at low SNR, corr-template at high SNR. Or run both and
OR. Plausible +0.5 to +1.5 dB; mostly recovers margin for low-SNR fade
events.

### Recommended next 2 hardware experiments (disambiguation)

**Experiment 1 (cheap, runs in simulator first):** apply Fix #1 in code,
rerun the same A/B harness at WGN ∈ {−4, −8, −12}. Expect non-zero data
delivery at WGN:−8 and likely at WGN:−10.

**Experiment 2 (Wave-3-regression check):** bisect commits `9c3fc40` →
`eec768e` → `41ac734` on a 4-cell IONOS sweep at WGN ∈ {14, 0, −4} pinned
ROBUST_0. Cheap (~20 min). Refutes H7 if data delivery is stable across
all three commits; useful as a control measurement regardless.

### User decisions queued

1. **Preamble change scope.** Fix #1 changes wire format — old MFSK
   ROBUST_0 endpoints (any pre-this-fix mercury) cannot decode new
   preambles and vice versa. Same situation as the 2026-05-24 MFSK ACK
   change. Acceptable to ship as a hard cutover (current practice), or
   does the user want a TEST_CONNECTION negotiation flag (`CAP_LONG_PREAMBLE`)
   to allow graceful coexistence? My recommendation: **hard cutover**,
   matches current MFSK-evolution discipline. Backward-compat isn't worth
   the bit.
2. **Preamble M.** Should data preamble drop from M=32 to M=16 (H6
   secondary)? Plus: shares tone set with ACK/CONNECT/HAIL family, can
   reuse infrastructure. Minus: SLIGHTLY reduces sequence diversity vs
   data tones (M=32 data has 28 free tones after preamble; M=16 preamble
   in M=32 data would only reach the lower 16 bins, which would
   change the data spectrum). My recommendation: **keep M=32 for now**,
   only revisit if Fix #1 alone doesn't close the gap.
3. **Roll-out validation.** Phase 0 used the
   `tools/axis_walk_sweep.py --pin-config 100 --with-robust` harness. Should
   this fix follow the same protocol (pinned-ROBUST_0 IONOS sweep at WGN ∈
   {14, 6, 0, −4, −8, −12})? Recommendation: yes, plus reproduce on real
   HF if possible.

## §13. Matched-filter metric fix (pre-code, 2026-05-27)

**Status:** plan committed before code. Builds on §H1 (preamble 4→16) and §H2
(per_sym_floor 0.05→0.01) which already shipped on `fix/preamble-extend`
(commits 6d7e9f9, 325efec). This fix addresses the deeper structural issue
identified by the follow-up debug agent: extending the preamble buys nothing
if the metric form itself doesn't reward longer integration.

### §13.1 The bug

`time_sync_mfsk_corr` (`ofdm.cc:3074-3115`) computes per-symbol normalized
cosine-similarity² and then AVERAGES across symbols:

```
sym_metric_k = |corr_k|² / (e_template_k · e_rx_k)   # cosine² ∈ [0,1]
metric = (1/N) · Σ sym_metric_k                       # mean
threshold = 0.5                                       # absolute, length-invariant
```

For pure complex Gaussian noise of variance σ² per sample:
- `E[|corr_k|²] = e_template_k · σ²`
- `E[e_rx_k] = Nofdm · σ²`
- `E[sym_metric_k] ≈ 1/Nofdm` (per-symbol noise floor)
- `E[metric_noise] = 1/Nofdm` regardless of N

The mean does NOT improve with longer integration. Averaging reduces the
*variance* of the metric (by 1/N) but the *mean* is length-invariant.

**Consequence:** the threshold 0.5 has the same separation from noise mean
(~0.003) for N=4 and N=16. The 4→16 preamble extension we shipped buys
NO sensitivity gain through this detector — only the stochastic variance
reduction (√N) helps, but the threshold itself was set as an absolute
value, not a noise-stddev-aware bound.

Contrast `detect_ack_pattern` (CONNECT/HAIL/ACK, `ofdm.cc:3231+`): uses a
discrete COUNT of symbols-where-expected-tone-is-FFT-peak. Threshold
`matched ≥ 7/16` scales with sequence length. This metric DOES gain with
length — that's why CONNECT works at WGN:-8 where DATA preamble dies.

### §13.2 The fix

Change `time_sync_mfsk_corr` from MEAN of per-symbol cosine² to a SUM,
with the threshold scaling linearly with `template_nsymb`. Two-line code
change inside the existing loop structure:

```diff
- double metric = (valid_syms > 0) ? total_metric / valid_syms : 0.0;
+ double metric = total_metric;          // sum, not mean

  ...
- double threshold = 0.5;
+ // Threshold scales with template_nsymb: each preamble symbol contributes
+ // ~1.0 to the sum for a clean match, ~1/Nofdm for noise. A length-scaled
+ // threshold preserves false-alarm rate while gaining matched-filter SNR
+ // discrimination with longer preambles.
+ double threshold = 0.5 * template_nsymb;
```

### §13.3 Why this is the right form

**For signal under noise** (per-sym coherent SNR `γ = e_sym/σ²`):
- `E[sym_metric_k] ≈ γ/(γ+1)` (cosine² of signal vs signal+noise)
- `E[sum_signal] = N · γ/(γ+1)`
- For high γ: sum_signal → N (each symbol contributes ~1)
- For low γ (cliff): sum_signal → N · γ (proportional to N · per-sym SNR)

**For pure noise:**
- `E[sym_metric_k] = 1/Nofdm` (length-invariant)
- `E[sum_noise] = N/Nofdm`
- `Var[sym_metric_k] ≈ 1/Nofdm²` (exponential distribution, near-zero floor)
- `Stddev[sum_noise] ≈ √N/Nofdm`

**Detection-SNR (signal-mean above noise-mean, in stddev units):**
- `(sum_signal - sum_noise) / stddev_noise`
- `≈ (N·γ - N/Nofdm) / (√N/Nofdm)`
- `= √N · (Nofdm·γ - 1)`
- **Grows as √N** — the matched-filter integration gain.

For N=4→16 (4× integration): `+√4 = +2× = +6 dB` matched-filter detection
SNR. Matches the diagnosis's +6 dB claim AND matches the audit's
estimated cliff shift from WGN:-4 to WGN:-10.

**Why not the "global noise estimate" form the diagnosis proposed?**
The diagnosis proposed `denominator = E_template_total · noise_var_estimate`
where `noise_var = e_rx_total / (N·Nofdm)`. Math-equivalent for noise
(noise mean = 1.0, stddev = 1/√N) but: (a) data-content discrimination
gets weaker because data tones in same alphabet can sum to ~N·0.44 cosine²
without bound; (b) requires a fresh "noise estimate" computation that
contaminates with signal energy at the candidate position; (c) departs
from the existing per-symbol bounded form that has empirical track-record
against data-content false peaks (Bug #44 testimony: per-sym cosine² is
bounded ≤1, giving ≤ N total — natural ceiling).

Keeping per-symbol normalized cosine² and just changing MEAN → SUM
preserves the data-content discrimination (worst-case data ≤ N·0.44 stays
below threshold N·0.5) AND gives matched-filter √N gain. Minimal code
change, no new state, no global energy plumbing.

### §13.4 High-SNR no-regression argument

At high SNR (sigma=0, current `mfsk_data_preamble_passband_roundtrip_clean`
test):
- Per-symbol cosine² ≈ 1.0 for each of 16 symbols
- Old: mean = 1.0, threshold 0.5 → passes (margin 0.5)
- New: sum = 16.0, threshold 8.0 → passes (margin 8.0)

At N=4 (legacy NB MFSK, `narrowband_enabled && M==MOD_MFSK`):
- Per-symbol cosine² ≈ 1.0 for each of 8 NB symbols
- Old: mean = 1.0, threshold 0.5 → passes (margin 0.5)
- New: sum = 8.0, threshold 4.0 → passes (margin 4.0)

Both cases preserve a 2× margin between signal and threshold, identical
structural relationship to the old behavior. No high-SNR regression.

### §13.5 Phase 2 refinement loop

`time_sync_mfsk_corr` has TWO instances of the metric computation: Phase 1
coarse search (`ofdm.cc:3074-3115`) and Phase 2 fine refinement
(`ofdm.cc:3176-3211`). Both compute the same sym_metric averaging. The
fix applies to BOTH (same MEAN → SUM change). The early-exit checks at
`ofdm.cc:3146` (`metric > 0.5`) and `ofdm.cc:3222` (`best_fine_metric > 0.5`)
must also be updated — they're "good enough to stop searching" cutoffs and
must scale with the threshold.

### §13.6 Fail-before-passes regression test

New test `mfsk_data_preamble_cliff_sigma` in `mfsk_ctrl_codec_tests.cc`:

1. Calls `ts.load_configuration(ROBUST_0)` (WB MFSK M=32, 16-sym preamble).
2. Generates the preamble (same as the existing
   `mfsk_data_preamble_passband_roundtrip_clean` test).
3. Round-trips through baseband_to_passband / passband_to_baseband.
4. ADDS WGN at a per-sample SNR matching WGN:-8 (in-band, computed from
   passband signal energy / per-sample noise variance).
5. Invokes `time_sync_mfsk_corr` and asserts `delay >= 0` AND
   `metric >= threshold` (where threshold is the new scaled value).

The cliff-SNR target: the IONOS WGN:-8 cell corresponds to a per-sample
passband SNR of approximately -10 to -12 dB after the FIR_rx_time_sync
bandpass (which gives the in-band signal). We pick a per-sample SNR
that's the BOUNDARY case: detectable with the new form, NOT detectable
with the old form. Deterministic PRNG seed makes the test reproducible.

**Validation:** before committing the metric change, run the test against
the unmodified `ofdm.cc` and verify it FAILS (returns delay=-1 or metric
below the old 0.5). After the change, verify it PASSES (returns
delay≥0 with metric above new scaled threshold). Document the metric
values produced in both cases.

### §13.7 Cross-layer audit

`time_sync_mfsk_corr` is invoked from exactly ONE production site
(`telecom_system.cc:1037` in `cl_telecom_system::receive_msg`, MFSK
branch). The function returns `delay` (sample index) and an out-parameter
`metric`. Callers use:
- `delay` to seek into the RX buffer for frame extraction
- `metric` for diagnostic logging only (no downstream policy decisions)

**Consumer impact of new metric form:**
- `receive_stats.delay = -1` on no-detect → unchanged (return value -1 in
  both old and new forms when metric < threshold)
- `receive_stats.delay >= 0` on detect → unchanged (sample index)
- Any log lines printing the metric value will now show 4× higher
  numbers for WB MFSK 16-sym preamble (sum vs mean). The OFDM-DSP
  fact doc and any log-parsing tools should be aware. Grep for
  `mfsk_sync_metric` in the source tree to identify diagnostic prints.

There is no Q-table, gearshift, or ARQ-state code that reads `out_metric`
in a way that affects flow control — confirmed by greps in the audit at
`data-flow-preamble_nSymb.md` §2.2. Diagnostic-only.

### §13.8 No regression to other test paths

The existing 17 tests in `mercury.exe --test` all run at sigma=0 (clean
loopback). At sigma=0:
- Per-sym cosine² ≈ 1.0 → sum ≈ N
- New threshold = 0.5·N → sum >> threshold by factor 2

All clean-channel tests pass without modification. The metric output
field in test diagnostics will change in magnitude but the pass/fail
decisions are preserved.
